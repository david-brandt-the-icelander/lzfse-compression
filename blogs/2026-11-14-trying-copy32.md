# Would a 32-byte copy beat `copy16`? We measured, and it did not

*2026-11-14. lzfse-zazzcat is an LZFSE compressor written from scratch in C, with the goal of beating Apple's
`libcompression` on Apple Silicon.*

The decoder's hot loop moves bytes 16 at a time. `copy16` in `src/copy.h` is a `copy_bytes` with a constant size
of 16, which the compiler turns into one 16-byte load and one 16-byte store. On arm64 there is also an instruction
pair that moves 32 bytes at once (`ldp q` / `stp q`), and many fast decompressors use wider steps. So the question
for this session was simple: are there places in this code base where a `copy32` would be faster than `copy16`?

The earlier [memcpy audit](2026-11-14-auditing-a-memcpy-tuning-plan.md) had already narrowed the search. If wider
copies help anywhere, they help in the `copy16` loops in `copy.h`, not in the wrapper functions. This post follows
that lead to the end. The answer is no, and the numbers show why.

## Where `copy16` is used

There are two callers that matter:

- **`decode_token_fast`**, the decoder's fast path for one token: copy the literals, then copy the match from
  `distance` bytes back. Both LZFSE and LZVN decoding go through it.
- **`wild_copy`**, which the encoder uses to gather literal bytes into its block buffer.

Both write past the requested end. The callers keep `COPY_SLACK` (32) spare bytes after the destination for that,
and later output overwrites the extra bytes. This is what makes the copies cheap: the decoder checks the room once
per token instead of once per byte.

A 32-byte step also has a correctness constraint in the match copy. When the match source is `distance` bytes
back and the distance is shorter than the step, the step reads bytes it is about to write itself. `copy16` is
therefore used only when `distance >= 16`, and a `copy32` step would need `distance >= 32`.

## Step 1: find out what the copies actually copy

A wider step only helps a copy that needs more than one narrow step. Before writing any variant, we counted token
shapes. We used a throwaway copy of the source with counters inside `decode_token_fast`, and decoded three real
inputs: a 1.9 MB Claude Code session log, 16 MiB from the middle of `libclang.dylib`, and 16 MiB of macOS SDK
headers.

| | session log | clang binary | headers |
|---|---:|---:|---:|
| Literal runs of 0–16 bytes | 97.6% | 99.3% | ~100% |
| Matches of 1–16 bytes | 82.0% | 85.9% | 76.5% |
| Matches of 17–32 bytes | 8.2% | 10.7% | 14.2% |
| Matches over 32 bytes | 9.9% | 3.4% | 9.3% |
| Match distance ≥ 32 | 97.1% | 91.3% | 96.1% |
| Tokens sent to the slow path | 0.01% | 0.03% | 0.01% |

Two things stand out:

- **Literal copies are almost always one step already.** Fewer than 2.5% of tokens have more than 16 literals. A
  32-byte literal copy would add a store to every token in order to save a step on a few of them. We did not
  benchmark it, because the table already settles it.
- **Match copies are the only real candidate.** Between 12% and 24% of matches are longer than 16 bytes, and
  nearly all of them are at a distance of 32 or more, where a 32-byte step is allowed.

## Step 2: two variants of the match copy

The current code:

```c
if (distance >= 16) {
    copy16(out, match_source);
    for (size_t done = 16; done < match_length; done += 16) copy16(out + done, match_source + done);
} else if (distance >= 8) {
    ...
```

**Variant 1** uses 32-byte steps whenever the distance allows it:

```c
if (distance >= 32) {
    copy32(out, match_source);
    for (size_t done = 32; done < match_length; done += 32) copy32(out + done, match_source + done);
} else if (distance >= 16) {
    /* the old copy16 loop */
} else if (distance >= 8) {
    ...
```

**Variant 2** leaves the common short match exactly as it was. It copies 16 bytes first and switches to 32-byte
steps only when the match is longer:

```c
if (distance >= 16) {
    copy16(out, match_source);
    if (match_length > 16) {
        if (distance >= 32) {
            for (size_t done = 16; done < match_length; done += 32) copy32(out + done, match_source + done);
        } else {
            for (size_t done = 16; done < match_length; done += 16) copy16(out + done, match_source + done);
        }
    }
} else if (distance >= 8) {
    ...
```

`copy32` is `copy_bytes(destination, source, 32)`. The disassembly confirmed that it compiles to `ldp q` / `stp q`.
Both variants can write up to 31 bytes past the match, which still fits in `COPY_SLACK`.

## A test that knew more than the comment

Both variants failed the unit tests, and every failure had the same message: `wrote past the slack`.
`test_decode_token_fast_matches_reference` checks that the fast path writes at most 16 bytes past the end, which
is the promise in `copy.h`'s header comment. `COPY_SLACK` is 32, so the variants were memory-safe, but they broke
a promise the test enforces. That is a good test: it pins the documented contract, not only the buffer size. A
real `copy32` change would have to update the comment and the test together. For the experiment we confirmed that
nothing else failed, and went on to measure.

## Step 3: measure

We built each version with `make CPU_FLAGS=-mcpu=apple-m1` on an M1 Pro and ran `lzfse-bench --runs 11` on the
three inputs, in 64 KiB and 1 MiB chunks. The three builds ran in turn, three rounds each. Apple's speed drifts
between runs, so every result is taken relative to Apple's decoder in the same run, and then compared with the
baseline.

| Input / chunk size | Variant 1 | Variant 2 |
|---|---:|---:|
| session log, 64 KiB | −11.1% | −4.3% |
| session log, 1 MiB | −8.4% | −3.4% |
| clang binary, 64 KiB | −17.3% | −8.0% |
| clang binary, 1 MiB | −15.2% | −6.6% |
| headers, 64 KiB | −11.6% | −4.2% |
| headers, 1 MiB | −8.7% | −5.3% |

Both variants are slower on every input and both chunk sizes. Within each build, the three rounds agreed to about
1%, so these differences are not noise. Variant 1 loses up to 17%. Variant 2, which doesn't change the copy for
80% of matches, still loses 3–8%.

## Why? We don't know yet

We did not profile the variants, so these are hypotheses, not findings:

- **An extra branch that is hard to predict.** Both variants add a test of `distance >= 32`. It is cheap to run
  but depends on the data, and a wrong guess costs much more than the store it was meant to save. The binary has
  the most matches at distances of 16–31, and it lost the most.
- **A bigger loop body.** An earlier change got its largest gain by keeping the token loop's state in registers.
  A longer body with more branches can push some of that state back out to the stack.
- **Bigger stores where small ones were enough.** Variant 1 writes 32 bytes for matches that needed 16. Store
  bandwidth is limited, and on Apple's cores an `stp q` probably costs about as much as two plain stores.

What variant 2 does show is that the extra branch on its own costs more than the loop steps it removes. Matches of
17–32 bytes saved one loop step each, and the result was still a net loss.

## The rest of the list

- **The encoder's `wild_copy`** already unrolls its first two 16-byte steps, so a copy32 would only remove one
  branch that is almost always predicted correctly. The encoder's time goes to finding matches anyway.
- **x86** without AVX flags (the default build) compiles a 32-byte constant copy to two 16-byte moves, so it gains
  nothing there. We also can't measure x86 in this project.

## Outcome

No code changed. `copy16` stays, and the reason to try `copy32` again would be a change in the inputs: data whose
matches are mostly longer than 32 bytes. Our three samples don't look like that.

## Takeaways

- **Count before you widen.** Ten minutes of counters showed that literal copies almost never need a second step.
  That ruled out half the idea before any benchmark ran.
- **A wider instruction is not free if it needs a new branch.** The step that moves more bytes is cheap. The cost
  is in deciding when it is allowed.
- **Let tests enforce the contract, not just memory safety.** The overshoot test caught a change in behavior that
  the sanitizer would never report, because the extra writes stayed inside the buffer.
- **Measure relative to a reference in the same run.** Raw MB/s moves between runs. Ratios against Apple's
  decoder, taken run by run, gave differences small enough to trust within 1%.
