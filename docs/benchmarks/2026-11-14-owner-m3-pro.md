# Benchmark: lzfse-zazzcat vs Apple's libcompression on an M3 Pro

- **Date:** 2026-11-14
- **Commit:** `e2b0f36` (two tables, 64 KiB fast path, held-back match, indexing inside matches)
- **Machine:** the owner's work MacBook Pro, Apple M3 Pro (11 threads), macOS 27.2.1, on AC power.
- **Command:**
  ```bash
  cargo run --release -p lzfse-bench -- --runs 11 --synthetic <session log>
  ```
- **Inputs:** the harness's synthetic corpus, plus a real 552 MB Claude Code session log ("session log" below).
  It is a different file from the one in the M1 Pro reports.

## Summary

Each cell is our speed divided by Apple's. Above 1 means faster.

| Input | Encode | Decode | Parallel encode (11 threads) | Parallel decode (11 threads) |
|---|---:|---:|---:|---:|
| Session log (real) | 1.13–1.22 | 0.84–0.88 | 6.8–7.3 | 4.7–5.1 |
| Text | 1.36–1.40 | 0.98–1.03 | 6.4–8.5 | 4.2–4.9 |
| JSON + base64 | 1.28–2.20 | 0.99 | 4.7–9.2 | 4.8–6.2 |
| Binary | 0.95–0.98 | 0.88–0.93 | 4.3–5.8 | 3.8–4.7 |
| Noise | 2.3–2.6 | 41–55 | 5.8–8.5 | 20–28 |
| Zeros | 25–59 | 1.1–2.2 | 85–103 | 0.6–3.9 |

- **Ratio** (smaller is better):
  - **Session log:** 2.1% smaller than Apple's at 1 MiB chunks (0.1747 vs 0.1784) and 2.3% smaller whole (0.1567 vs
    0.1604, from `--stats`). Equal at 64 KiB chunks. Before the two-table and held-back-match changes it was 3.9%
    and 7.4% larger.
  - **Text:** 9–10% smaller.
  - **Binary:** 2–3% smaller.
  - **JSON + base64:** 0.3% larger at 64 KiB chunks, equal otherwise.
- **Where we still lose:**
  - single-threaded decoding of the session log (12–16% slower) and of binaries (7–12% slower);
  - single-threaded binary encoding (2–5% slower).
- **Zeros, 1 MiB chunks, parallel decode:** this is below single-threaded decoding. Each chunk compresses to a few
  bytes, so handing chunks to threads costs more than decoding them.
- **Zeros encode speed:** commit `523c6bc` dropped it to about 1,060 MB/s by indexing the inside of runs. `e2b0f36`
  restored it.
