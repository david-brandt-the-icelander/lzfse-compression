# Benchmark: lzfse-zazzcat vs Apple's libcompression on an M1 Pro (two-table encoder)

- **Date:** 2026-11-14
- **Commit:** `aa0710b` (two-table match finder and the 64 KiB fast path)
- **Machine:** the owner's MacBook Pro, Apple M1 Pro (10 threads), macOS 27.0.1.
- **Command:**
  ```bash
  cargo run --release -p lzfse-bench -- --runs 11 --synthetic <session log>
  ```
- **Inputs:** the harness's synthetic corpus, plus the same real Claude Code session log as the
  [2026-11-13 run](2026-11-13-owner-m1-pro.md).

## Method notes

- **Comparing runs:** Apple's own speeds differ from the 2026-11-13 run by up to 15% (text encode 120 → 133 MB/s,
  session-log decode 1262 → 1394 MB/s). So compare runs by the ratios in the summary, which come from contenders
  timed back to back within one run, rather than by absolute numbers.
- **Order:** the contender that runs first now rotates each run.
- **Correctness gate:** every chunk was decoded by both decoders before its timing counted.

## Summary

Each cell is our speed divided by Apple's, with the 2026-11-13 run in brackets. Above 1 means faster.

| Input | Encode | Decode | Parallel encode (10 threads) | Parallel decode (10 threads) |
|---|---:|---:|---:|---:|
| Session log (real) | 1.06–1.26 (1.09–1.39) | 1.00–1.02 (0.99–1.01) | 7.2–8.8 | 5.6–6.3 |
| Text | **1.34–1.35** (0.97–1.00) | **1.00–1.04** (0.75–0.76) | 9.0–9.7 | 5.0–6.0 |
| JSON + base64 | 1.24–2.10 (1.8–2.2) | 1.10 (1.09–1.11) | 6.3–10.1 | 6.1–7.0 |
| Binary | 0.91–0.95 (0.87–1.03) | **0.90–0.95** (0.83–0.87) | 6.2–6.4 | 5.0–5.6 |
| Noise | 2.1–2.3 | 46–61 | 4.0–9.2 | 27–32 |
| Zeros | 22–54 | 1.1–2.3 | 81–113 | 1.1–4.1 |

- **Ratio** (smaller is better):
  - **Text:** 9–10% smaller than Apple's.
  - **Binary:** 2–3% smaller.
  - **Real session log:** within 0.3% of Apple's: 0.2% larger at 64 KiB chunks, 0.3% smaller at 1 MiB chunks and whole.
  - **JSON + base64:** 0.3% larger at 64 KiB chunks, equal otherwise.
- **What changed:** longer matches mean fewer tokens, which closed the text-decoding gap (from 24% behind to on
  par) and narrowed the binary one.
- **Where we still lose:** single-threaded binary encoding (5–9% slower) and decoding (5–10% slower).
